# Lessville + LessDB Agent-Native Review

**Date:** 2026-10-08  
**Scope:** continue the open work on (1) making Lessville a more believable small-world simulation and (2) making LessDB a natural fit for agents whose database access is driven by situation and awareness rather than retrofitted SQL calls.

## Executive conclusion

The project has two different kinds of work that must remain connected but not conflated:

1. **Lessville needs causal world state.** Characters already have named routines, movement, messages, memories and decisions, but several important things are still strings, timers or instantaneous mutations. A believable small world needs explicit state transitions for places, objects, commitments and action outcomes.
2. **LessDB needs a first-class agent context contract.** LessDB already has strong primitives—SQL, graph/context notes, memory tables, vectors, MCP identity, tenancy and audit—but the agent still has to decide how to assemble a situation, search memories, filter permissions, select provenance and fit the result into a context window. Lessville currently demonstrates that assembly in application code (`sim.rs` and `llm.rs`). That is useful evidence, but it is still an adapter, not an agent-native database primitive.

The right next step is **not** to add more decorative locations or more raw MCP tools. It is to make the causal contract explicit, prove it in Lessville, and then promote the reusable parts into LessDB.

> **Design rule:** the application owns policy and action execution; LessDB owns durable context, retrieval, provenance, identity, governance and efficient query execution. Neither layer should pretend to own the other’s guarantees.

## 1. Current baseline

### Lessville already demonstrates

- Five distinct fictional agents: Maya, Bo, Lin, Sam and Ama, with Mochi as a non-agent companion.
- A shared persisted Asia/Singapore simulated clock, day/night cycle, movement, interiors, bus presentation and weather.
- Real embedded LessDB writes for memories, messages, decisions, events, scope membership, access checks, checkpoints and model-call provenance.
- Application-layer scope filtering that is visible in the UI and explicitly labelled as **not native LessDB ACL**.
- Deterministic, versioned policies. The optional model only voices selected lines and creates bounded nightly reflections; it does not choose actions.
- Cloud deployment with R2 checkpointing, observer-only public access and a hard 9,500-neuron daily model budget.

### Lessville still has correctness gaps

The realism audit found that the most important state is not yet causal enough:

- Café open/closed state is implied by Maya’s activity; lights, door, till, espresso, fridge and table state are not authoritative fields.
- An oat-milk shortage can silently become a dairy latte without customer acceptance, without consuming milk stock and despite Lin’s private dairy constraint.
- Table holds are temporary memories but do not reserve a named table object or emit a release/occupancy transition.
- The bus is generated by a modulo-20 loop, while the visual and narrative flows imply named trips. A delayed 08:00 service can appear five simulated minutes before the 08:20 service, and the delayed trip can disappear from `bus.next` while `buses()` still waits for it.
- Lin’s inbound and return bus plans can alight directly at the stop without a complete application-owned bus travel interval.
- Sam’s declared arrival windows do not match generic eight-minute travel. His coffee disappears before the café-to-office walk, and the grocery bag is not explicitly put away at home.
- Ama’s grocery result is applied at arrival rather than at a browse/checkout/purchase transition.
- Station and animation are inferred from free-form activity strings. A wording change can silently render a contradictory pose.
- A temporary `status.dnd` memory is recorded for Lin but is not yet enforced at the interaction point.

These are not failures of LessDB storage. They are missing domain state and policy boundaries in the simulation service.

## 2. Front one — make Lessville a real small world

### 2.1 The causal model

A believable small world should make every visible outcome pass through five layers:

| Layer | Question | Example |
|---|---|---|
| **World time** | When can this happen? | Café is closed before opening and after close. |
| **Place/object state** | What is physically available? | Table 2 is free, held, occupied or released. |
| **Social state** | Who knows, promised or consented to what? | Sam’s errand acceptance shares one context ID with Ama’s request. |
| **Agent situation** | What can this agent currently perceive and recall? | Maya sees cafe-staff stock facts but not Lin’s private dairy reason. |
| **Action outcome** | What changed after the action completed? | Milk stock decremented only after an accepted drink is handed over. |

A rendered sprite, speech bubble or activity string must be downstream of these layers. It must not be the source of truth.

### 2.2 P0 implementation sequence

#### P0-A: explicit café service state and safe ordering

Add an application-owned café state to the persisted world snapshot:

```text
closed -> opening -> open -> closing -> closed
```

Also expose a small object state map:

```text
lights: off|on
front_door: locked|open
 till: closed|ready|serving|cashout
 espresso: off|heating|ready|busy
 fridge: closed|open
 tables: free|held|occupied|released
```

Use one order context ID for the complete interaction:

```text
order.request -> order.accepted|alternative.offered -> preparation -> handoff|declined
```

For missing oat milk, Maya must say that oat milk is unavailable and offer a documented alternative or refusal. The simulation must record the customer’s accepted choice. It must never silently serve dairy, expose Lin’s private reason, or decrement the wrong stock.

#### P0-B: authoritative transit service

Replace the implicit modulo-20 bus calculation with a named timetable structure consumed by:

- bus arrival logic;
- `snapshot().bus.next`;
- rider boarding/alighting;
- renderer phase and ETA;
- delay nudges and stored delay memories.

Each trip needs a stable identity, route/direction, scheduled time, effective time, phase and rider set. A delayed trip remains visible as the active next trip until it arrives. Lin’s inbound and return rides must have a real `travel.mode = bus` interval from boarding through alighting.

#### P0-C: explicit action outcomes and object lifecycles

Apply state changes at action completion, not at the first arrival frame:

- Sam: coffee = ordered → carried → consumed/left at office.
- Sam: eggs = absent → purchased at checkout → bag carried → put away at home.
- Ama: browse → checkout → bag carried → put away.
- Maya: supplier order → carrying oat milk → stock increased on return to the café.
- Lin: backpack acquired before boarding and intentionally dropped/retained at dorm.

Each meaningful transition gets one concise event row with its context and provenance.

#### P0-D: stable activity vocabulary

Stop deriving station semantics from arbitrary prose. Add explicit fields to the service model:

```text
activity_kind = opening|serving|checking_stock|commuting|typing|meeting|cooking|shopping|checkout|studying|riding_bus|closing|sleeping
station = till|espresso|fridge|desk|meeting|kitchen|aisle|checkout|table1|table2|shelter|bus_seat|...
pose = idle|walk_front|walk_back|walk_side|talk|type|cook|seat|carry|workout
```

The client can still display a human sentence, but it should render from these bounded fields and use a safe explicit fallback.

### 2.3 P1 small-world depth

After the P0 state model is stable:

- Add the office stand-up and report-progress event/message as real records, not only bubbles.
- Add a minimal family dinner event linking Ama, Sam and Mochi.
- Enforce Lin’s unexpired DND preference at the smallest staff-interaction boundary.
- Add object-level conflict checks for tables and errands.
- Add a small named relationship graph (family, staff, regular, coworker) with changes recorded as events; do not invent rich psychology before these relationships are causal.
- Keep furniture-aware pathfinding, extra ambient townspeople and broad idle-animation expansion as later work.

### 2.4 Acceptance gates for Lessville

A scenario is complete only when all four views agree:

1. **World state:** the service state is physically and temporally consistent.
2. **LessDB rows:** the relevant event/message/memory/decision rows exist with context and provenance.
3. **Agent recall:** the intended agent sees the right rows and hidden rows remain hidden under the application rule.
4. **Rendering:** the town/interior/UI shows the same state without inventing a transition.

The first regression corpus should cover:

- café lifecycle and a declined/alternative oat order;
- table hold conflict, occupancy and expiry;
- named delayed bus trip at speeds 1, 4 and 8;
- Sam coffee and eggs lifecycles;
- Lin bus travel, DND and backpack;
- Maya restock not increasing café stock until return.

## 3. Front two — make LessDB natural for agents

### 3.1 What is missing today

LessDB’s current product is already stronger than a typical memory wrapper:

- one analytical engine for humans and agents;
- graph/context notes, memory tables and vectors in one data directory;
- MCP tools with tenant namespaces, roles and audit logging;
- SQL and Arrow interoperability;
- explicit provenance and governance direction.

The missing abstraction is **situation-aware context assembly**. Today an agent-facing application must do all of this itself:

1. identify the agent and its effective permissions;
2. describe the present situation;
3. choose which memory kinds and time/spatial windows matter;
4. perform multiple retrieval queries;
5. merge graph, tabular, vector and message results;
6. deduplicate and rank them;
7. keep provenance and scope labels;
8. fit the result to a token/latency budget;
9. log what was offered to the model and what was actually used.

Lessville’s `llm.rs` already exposes this problem: it directly constructs a bounded SQL query over `lv_memories`, adds a few rows to a prompt and records memory IDs. That is a good experimental adapter, but it is not yet a reusable LessDB capability.

### 3.2 Agent Context Contract v0

The first agent-native contract should be transport-neutral and usable from Rust, MCP, Python and Node:

```text
AgentIdentity
  agent_id
  tenant
  role
  scopes / grants
  policy_version

Situation
  context_id
  observed_at
  logical_time + timezone
  location / spatial anchor
  current activity
  nearby entities
  active goals and commitments
  current world conditions
  allowed actions

RecallIntent
  task_id
  purpose
  query terms / tags
  memory kinds
  temporal window
  spatial window
  relationship scope
  max items / max bytes
  freshness requirement

ContextItem
  item_id
  kind
  content or structured payload
  owner / source agent
  scope decision
  relevance explanation
  source references
  created_at / valid_from / valid_until

ContextPacket
  context_id
  situation
  items
  messages
  constraints
  provenance
  budget used / remaining
  omitted-count and omission reasons
```

Important distinctions:

- **Situation is not memory.** It is the present query frame.
- **Recall is not prompt stuffing.** It is a bounded, permission-aware database operation.
- **Provenance is not a citation added later.** It is part of each returned item.
- **Expiry is not forgetting.** A row may be expired, archived, revoked or deleted; those must remain distinguishable.
- **A policy decision is not a model completion.** LessDB records what context was offered; the application decides what to do.

### 3.3 Proposed LessDB primitives

Promote the contract in stages, without replacing SQL or MCP:

#### Stage A — context broker API above existing stores

Create a small `less-agent` Rust crate (or an equivalent module during incubation) that composes existing graph, memory, vector and SQL surfaces. It should provide:

- `open_agent_session(identity, policy)`;
- `observe(situation)`;
- `recall(intent)`;
- `context_packet()`;
- `remember(item, retention, scope, provenance)`;
- `record_decision(decision)`;
- `explain_context(context_id)`.

The broker must use existing LessDB primitives and make no new storage guarantee claims. It is the correct place to test ranking, deduplication, context budgets and provenance before committing to a storage-level design.

#### Stage B — MCP tools designed around agent tasks

Add a small number of high-value tools rather than many low-level wrappers:

- `agent_session_open` — identity, tenant, policy version and default budgets;
- `agent_observe` — current situation and active commitments;
- `agent_recall` — bounded, permission-aware retrieval across context/memory/graph/vector sources;
- `agent_remember` — typed memory with retention, scope, source and confidence/uncertainty fields;
- `agent_decide` — record a decision with recalled item IDs and policy/model provenance;
- `agent_context_explain` — reproduce why an item was included or omitted.

Raw `lessdb_query` remains available to authorized users and analysts. The agent tools should be the default for agents because they carry identity, intent, budgets and provenance as structured inputs.

#### Stage C — native governance and temporal semantics

Promote only the semantics that survive real use:

- query-time row/column grants for agent identity;
- explicit valid-time versus transaction-time fields;
- archival state distinct from expiry and deletion;
- approval/proposal flow for destructive or schema-changing agent writes;
- immutable context-access audit entries;
- native entity and relationship provenance.

These are important LessDB goals, but they should not be claimed merely because an application wrapper currently filters rows.

### 3.4 LessVille as the proving ground

Lessville should stop calling the model gateway with an ad hoc context string and instead use the same context contract we want to publish:

```text
Situation: Lin at cafe/table1, studying, 08:20 SGT
Task: phrase one already chosen line
Recall intent: visible consented cafe preference, last 3 relevant memories
Constraints: <=18 words, no new facts, no private dairy reason
Result: ContextPacket with item IDs + scopes + provenance
Action: deterministic service policy; model may only re-voice
```

The UI should expose the packet summary:

- situation used;
- items included;
- items hidden and why;
- context budget;
- policy version;
- model call status;
- resulting event/decision references.

This makes the demo show the natural agent/database loop instead of showing a database query bolted onto a game.

## 4. What not to do

- Do not add an LLM planner that silently controls the world. The current deterministic-policy boundary is a strength.
- Do not make LessDB responsible for café schedules, bus physics or character psychology. Those belong to the simulation/application layer.
- Do not call application-layer scope predicates native ACL.
- Do not treat vector similarity as the context contract. Situation, permissions, temporal validity and provenance must constrain retrieval before ranking.
- Do not add more MCP tools until the structured agent-session and recall semantics are clear.
- Do not widen the public Lessville model budget or infrastructure budget during this milestone.

## 5. Recommended execution order

### Milestone 1 — causal Lessville core

1. Café lifecycle and safe ingredient interaction.
2. Named bus timetable and complete ride interval.
3. Stable activity/station/pose fields.
4. Sam/Ama/Lin object transitions and explicit action events.
5. Scenario regression corpus at speeds 1, 4 and 8.

### Milestone 2 — context broker incubation

1. Define Rust structs for `AgentIdentity`, `Situation`, `RecallIntent`, `ContextItem` and `ContextPacket`.
2. Move Lessville model context assembly behind the broker.
3. Add `/api/agent/:id/context` as an observability endpoint, not a new permission claim.
4. Show included/omitted context and provenance in the UI.
5. Measure prompt size, latency, duplicate rate and hidden-row correctness.

### Milestone 3 — LessDB productization

1. Add a `less-agent` crate over existing stores.
2. Add the six agent-session MCP tools with structured schemas.
3. Add context explainability and budget telemetry.
4. Add native grants/valid-time/archival semantics only after the broker tests define expected behavior.
5. Re-run Lessville against the published agent-native API, while retaining SQL as the human/analyst door.

## Decision

Proceed with **Milestone 1 and the context-broker contract in parallel**, but keep the implementation boundary explicit:

- Lessville proves causal world state and agent behavior.
- LessDB receives a reusable, governed context interface only after Lessville demonstrates the retrieval and provenance requirements.

This is the shortest path to an agent-first database that is genuinely natural for agents rather than a conventional SQL database with an agent label attached afterward.

## 6. Implementation status — 2026-10-09

The first production-shaped slice is now in the Lessville source checkpoint:

- **Café lifecycle:** `closed → opening → open → closing` is explicit in the
  snapshot; orders write `requested`, `accepted` or `alternative_offered`,
  `preparing`, and `handed_off`/`declined` rows to `lv_orders`.
- **Safe ingredient behavior:** an oat shortage offers a visible alternative;
  Lin declines rather than silently receiving dairy. Deterministic policies and
  optional model phrasing remain separate.
- **Named bus records:** snapshots expose a route, direction, scheduled/effective
  time, trip ID and phase using one shared timetable helper.
- **Stable render state:** agents now persist bounded `activity_kind`, `station`
  and `pose` fields; human-readable activity is explanatory copy, not a client
  parsing contract.
- **Object provenance:** café ingredients, eggs and supplier stock record explicit
  handoff transitions in `lv_object_transitions`.
- **Context observability:** `/api/agent/{id}/context` is read-only and returns
  situation, bounded items, content size and the application-layer visibility
  boundary. The Mind panel displays the packet summary.

The full MCP agent-session family, native row grants, valid-time semantics,
transactional action execution and scenario-speed regression corpus remain open.
No deployment was performed for this slice.

## 7. Implementation status — 2026-10-11 realism follow-up

The next world-model slice is implemented locally and remains deliberately
application-owned:

- seeded weather transitions expose condition, temperature, wind and change
  time; weather-aware behaviour is visible in the snapshot and context packet;
- a bounded occupation transition demonstrates that an agent can evolve over
  time through an event plus permanent memory rather than a mutable label only;
- eight background residents follow stable route targets and carry ordinary
  occupation/activity/mood fields for town population;
- the bus renderer consumes an authoritative finite active-trip phase and ID,
  while the walker renderer turns before short path segments are consumed;
- restored snapshots hydrate missing fields so older LessVille worlds remain
  readable.

These changes make the simulation more believable, but they do not move
weather, occupation, crowd movement or bus physics into LessDB. LessDB stores
the resulting events, memories, decisions and snapshots; the causal rules
remain in the LessVille application. The backend API smoke test exposed the
new fields from a freshly built executable, and the existing SC-01–SC-03
scenario suite still passes. Production deployment remains intentionally
deferred until a staging review checks the richer visual density and bus
timing at several simulation speeds.
